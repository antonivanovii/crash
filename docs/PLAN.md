## Ключевое отличие от витрины

В витрине игра — это чёрный ящик в iframe, и фронтенд занимается только оболочкой. У тебя игра — это твой код, работающий с твоим же WebSocket и твоим леджером. Значит:

- Оболочка и игра делят одно соединение, один стор баланса, одну сессию
- Переход между играми не перезагружает соединение
- Игровой рантайм можно вынести в общий слой, который переиспользуют все игры

Последнее — главный архитектурный выигрыш. Разберу его первым.

## Игровой рантайм: один слой на все игры

Из разбора игр видно, что все они складываются из трёх примитивов:

**Атомарная ставка** — Limbo, Dice, Plinko, Wheel, Keno, слот в базовой игре. Запрос, ответ, отрисовка.

**Открытый раунд** — Mines, Towers, фриспины. Состояние на сервере, несколько запросов, восстановление при реконнекте.

**Общий раунд** — Crash, рулетка, Dragon Tiger, общий тираж. Оркестратор, фазы, события в pub/sub.

Это три хука, а не тридцать реализаций:

```ts
useAtomicBet(game); // → { play, state, lastResult, isPending }
useOpenRound(game); // → { start, act, cashout, round, restore }
useSharedRound(game); // → { phase, roundId, startedAt, bet, snapshot }
```

Каждый инкапсулирует идемпотентность (генерация ключа, ретрай), оптимистичное состояние кнопки, обработку отказов по лимиту и балансу, реконнект. Конкретная игра получает только `(result) => отрисовка`.

Практически это значит: после того как написан Mines, Towers — это новый компонент отрисовки поверх `useOpenRound` и новая функция множителя. День работы, как я и говорил.

## Разделение «логика — представление» на клиенте

Внутри игры держи ту же границу, что на сервере:

```
games/mines/
  engine.ts       — чистые функции: множители, вероятности, валидация клика
  useMines.ts     — состояние раунда поверх useOpenRound
  MinesBoard.tsx  — отрисовка
  Mines.tsx       — сборка
```

`engine.ts` **должен быть общим с бэкендом** — один пакет в монорепе. Формула множителя Mines не должна существовать в двух местах: разъедутся при первой правке, и игрок увидит на экране одно, а получит другое. Это ровно тот класс багов, который убивает доверие.

## Рендер: где React, а где нет

Граница простая — по частоте кадров.

React отрисовывает всё, что меняется по событию: панель ставки, кнопки, историю, баланс, результат. Здесь React идеален.

Всё, что перерисовывается каждый кадр, React рисовать не должен:

- **Crash** — кривая и растущее число. Canvas, `requestAnimationFrame`, ноль ре-рендеров React за раунд. Множитель пишется прямо в canvas или в DOM-узел через ref.
- **Plinko** — шары в полёте. Canvas обязательно, двадцать шаров DOM-элементами не вытянет.
- **Слот** — вращение барабанов. Canvas или WebGL.
- **Limbo, Mines, Towers, рулетка, Dragon Tiger** — DOM и CSS-переходы достаточно. Roll-up числа в Limbo — через ref, без `setState` на каждый кадр.

Типичная ошибка — держать анимируемое значение в React-стейте. Шестьдесят ре-рендеров в секунду с полным пересчётом дерева, при том что меняется одна строка текста.

## WebSocket-слой

Одно соединение на всё приложение, живёт в провайдере над роутером. Что должно быть внутри:

- **Реконнект с экспоненциальной задержкой** и обязательный запрос снапшота после восстановления. Не «продолжить с того места» — именно полный снапшот: фаза общего раунда, свой открытый раунд, баланс.
- **Оценка смещения часов** по round-trip при подключении. Нужна для crash и для таймеров фаз.
- **Подписка по комнатам:** зашёл в crash — подписался на его комнату, вышел — отписался. Иначе клиент получает события всех игр сразу.
- **Батчинг входящих** — кэшауты в crash приходят пачками, разворачивать их в отдельные ре-рендеры не надо.

Баланс приходит только по сокету, из одного источника. Никаких вычислений баланса на клиенте: локальный счётчик допустим как визуальная интерполяция (шары в полёте в Plinko), но при каждом серверном обновлении он снапится к серверному значению.

## Provably fair как часть фронта

Это не сноска в футере, а рабочий раздел, и он на клиенте:

- Верификатор, который пересчитывает результат в браузере тем же кодом из общего пакета
- История сидов с раскрытыми серверными и возможностью проверить любой раунд
- Смена клиентского сида
- Для crash и общих игр — проверка звена цепочки: `SHA256(seed_i) == seed_{i-1}`
- Для слота — опубликованные полосы и таблица выплат с хэшем модели

Раз `engine.ts` общий, верификатор — это буквально вызов той же функции. Двадцать строк кода и главный аргумент продукта.

## Стек

Что я бы взял:

- **Vite**, не Next. SSR тут не нужен: приложение за авторизацией, SEO неактуально, а Next добавляет гидратацию, которая с сокетами и canvas только мешает.
- **TanStack Router** или React Router с ленивыми чанками по разделам
- **React Query** для серверного состояния, **Zustand** для сокетного, локальный стейт для UI
- **Монорепа** (pnpm workspaces или Turborepo): `packages/game-engine` разделяемый между фронтом и Nest
- **Canvas 2D** для crash и Plinko, PixiJS — только если возьмёшься за слот
- **Zod** на границе API, схемы тоже в общем пакете

## Структура

```
apps/
  web/          — React
  api/          — NestJS
  orchestrator/ — воркер общих раундов
packages/
  game-engine/  — чистая математика всех игр + провably fair
  contracts/    — Zod-схемы, типы событий сокета
  ui/           — дизайн-система
```

Оркестратор отдельным приложением с самого начала. Мы разбирали, почему таймеры раундов не должны жить в каждом инстансе API — если это не разделено на уровне структуры, разделить потом будет больно.

## Порядок сборки

Я бы шёл так:

1. Оболочка, авторизация, кошелёк, леджер, WebSocket-слой
2. Limbo — тонкий вертикальный срез через всё: идемпотентность, блокировки, seed-цепочка, верификатор
3. `useAtomicBet` выделяется из Limbo, поверх него Dice и Plinko
4. Mines и `useOpenRound`, затем Towers почти бесплатно
5. Оркестратор и Crash — первая игра Тир 2, самая дорогая
6. Рулетка и остальное Тир 2 поверх готового оркестратора

Первые два шага — это половина всей работы. Дальше стоимость каждой игры падает резко, и вот тогда каталог наполняется быстро.
