# Архитектура

## Четыре приложения, не микросервисы

```
apps/api/            NestJS + Fastify — HTTP и WebSocket-гейтвей
apps/orchestrator/   воркер общих раундов, синглтон с leader election
apps/settler/        фоновый воркер: расчёт, сверка, отчёты
apps/admin-api/      операторские эндпоинты, отдельная сеть и доступ
```

Это модульный монолит, разрезанный по **свойству процесса**, а не по домену.

`api` горизонтально масштабируется и не имеет состояния. `orchestrator` —
синглтон, потому что таймер раунда обязан тикать ровно в одном месте.
`settler` фоновый: переживает падения и ретраит. `admin-api` изолирован.

Домены при этом остаются модулями Nest внутри `api`. Резать по доменам
сейчас — получить распределённые транзакции там, где нужна одна.

## Общие пакеты

```
packages/money/       BigInt в минорных единицах, округления, форматирование
packages/game-engine/ чистая математика игр + provably fair
packages/contracts/   zod-схемы и типы событий сокета
packages/db/          схема Kysely, миграции, кодек NUMERIC ↔ bigint
packages/ui/          дизайн-система: токены и примитивы
```

`game-engine` общий между фронтом и Nest намеренно. Формула множителя Mines
не должна существовать в двух местах: разъедутся при первой правке, и игрок
увидит на экране одно, а получит другое. Из этого же следует, что верификатор
на клиенте — вызов той же функции, которой считал сервер.

## Деньги

`NUMERIC(38,0)` в минорных единицах, `bigint` в TypeScript. Ни на одном шаге
не появляется float.

Драйвер настроен так, что `NUMERIC` парсится сразу в `BigInt`
(`packages/db/src/client.ts`) — иначе он тихо превратится в `number` и потеряет
точность на больших значениях. На проводе сумма всегда строка: JSON не умеет
bigint, а `number` теряет точность начиная с 2⁵³.

Конвертация в строку на выходе — глобальный интерсептор
(`common/serialization/bigint.interceptor.ts`), а не дисциплина в контроллерах.

Отдельная ловушка: `pg` принимает bigint как значение `NUMERIC`, но роняет
запрос на bigint **внутри** jsonb. Поэтому jsonb пишется через `toJsonb()`.

## Инварианты живут в схеме

Что можно нарушить в коде, будет нарушено. Что нельзя нарушить в схеме — нет.

```sql
CREATE UNIQUE INDEX ON transactions (idempotency_key);
CREATE UNIQUE INDEX ON rounds (user_id, game) WHERE status = 'ACTIVE';
CREATE UNIQUE INDEX ON seed_pairs (user_id) WHERE active;
CREATE UNIQUE INDEX ON bets (seed_pair_id, nonce);
CHECK (balance >= 0)
CONSTRAINT TRIGGER entries_balanced DEFERRABLE INITIALLY DEFERRED
```

Триггер `entries_balanced` проверяет, что сумма проводок транзакции равна нулю.
Отложенный — потому что проводки вставляются по одной и промежуточные
состояния законно неуравновешены.

## Транзакционный контур

Каноническая форма — `apps/api/src/modules/games/_shared/bet.service.ts`.
Порядок шагов не декоративный:

1. **Идемпотентность** — ретрай возвращает ту же ставку, а не делает новую.
2. **Блокировка кошелька** — до всех проверок, чтобы между проверкой
   и списанием не влезла вторая ставка.
3. **Лимиты** — внутри той же транзакции, иначе обходятся параллелизмом.
4. **Чистая функция** из `game-engine`.
5. **Двойная запись**.
6. **Запись входов вместе с результатом** — иначе раунд не воспроизвести.

Порядок блокировок во всём проекте один: сначала кошелёк, потом раунд или
исход. Разный порядок в разных местах даёт дедлоки, которые воспроизводятся
раз в неделю.

Изоляция — `READ COMMITTED` с явными `FOR UPDATE`. `SERIALIZABLE` заманчив,
но даёт ретраи на конфликтах там, где явная блокировка их не даёт.

Результат вычисляется внутри транзакции, но раскрывается только после коммита:
показать игроку ролл и откатить транзакцию — значит переиспользовать nonce
и получить на нём другой результат.

## Идемпотентность

Две сущности, и это не дублирование:

- `transactions.idempotency_key` с уникальным индексом — гарантия, что денежная
  операция не выполнится дважды;
- `idempotency_keys` — кеш ответа. Клиент, потерявший ответ на сети, должен
  получить **тот же** ответ, а не ошибку уникальности.

Ключ приходит в заголовке `idempotency-key`, разбирается интерсептором
(`@Idempotent()`), а не руками в каждом сервисе. Тот же ключ с другим телом —
`IDEMPOTENCY_KEY_REUSED`: это баг клиента, а не повтор.

Для составной операции ключ покрывает **набор**: двадцать фишек на рулетке —
один ключ на всю раскладку.

## Redis

Три роли, три логические БД: pub/sub раундов, блокировка лидера, кеш
и rate limit.

Чего в Redis нет: денег, состояния раунда, точки краха. Redis может исчезнуть
целиком — раунд обязан доиграться из Postgres.

## Очереди

BullMQ. Через него идёт то, что может подождать: расчёт спорта, разрешение
рынков, опрос провайдеров, раскрытие сидов, ночная сверка, отчёты.

Через него **не** идёт ничего, где игрок ждёт ответа: приём ставки, кэшаут
в crash, любое движение денег в реальном времени.

## Реалтайм

```
orchestrator → Redis pub/sub → gateway (N инстансов) → клиенты
```

Гейтвеи stateless и без логики раунда. Они умеют: аутентифицировать сокет,
подписать на комнату, отдать снапшот, транслировать.

Множитель crash не транслируется — он детерминированная функция времени,
клиент считает его сам от `startedAt` с поправкой на смещение часов. Сервер
шлёт три вида событий: старт, кэшауты пачками по 100 мс, крах. Иначе на
каждого подключённого уходит 60 сообщений в секунду вместо трёх на раунд.

Точка краха и `startedAt` пишутся в БД **до** перехода в RUNNING. Иначе
падение оркестратора становится способом отменить неудобный раунд — а это
уже не надёжность, а честность.

## Валидация

zod в `packages/contracts`, схемы общие с фронтом. Глобального
`ValidationPipe` в `api` нет намеренно: вторая система валидации означала бы
две правды о том, что считается корректной ставкой.

Границы игр берутся из движка, а не дублируются числами: правка кап-множителя
в одном месте меняет и валидацию.

## Миграции

Только вперёд. Накатываются до деплоя кода, код совместим с двумя соседними
версиями схемы. `down` существует для локальной разработки — откат схемы
на живой базе это не откат, а новая миграция.
